Abstract

   This document specifies the DTN Basket Protocol, a binary application
   schema based on CBOR (RFC 8949) designed for the aggregation, multi-
   requesting, and synchronous/asynchronous transfer of resources in
   delay-tolerant networks (DTNs) utilizing the Bundle Protocol Version
   7 (RFC 9171).  The protocol separates the control plane (structured
   metadata and CoAP statuses) from the data plane (raw content
   transmitted in distinct bundles).

1.  Introduction

   In disconnected or intermittent networks governed by the Bundle
   Protocol v7 (BPv7, [RFC9171]), reducing network overhead is critical.
   The DTN Basket Protocol allows the aggregation of multiple
   heterogeneous requests (retrieval, verification, search,
   cancellation, listing) within a single basket encoded in CBOR
   ([RFC8949]).



F4JXQ                   Expires 11 February 2027                [Page 2]

Internet-Draft             DTN Basket Protocol               August 2026


   To ensure data integrity under BPSec ([RFC9182]) while permitting
   partial responses by intermediary nodes, the protocol separates
   control and content:

   *  A CBOR control bundle (basket-response) carrying only metadata and
      application execution statuses.

   *  Native BPv7 network bundles carrying the raw payloads of each
      resource.

2.  Terminology

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",

3.  Protocol Specification (CDDL)

   The exact syntactical structure of the request basket and the
   response envelope is defined below in CDDL ([RFC8610]).

   ; =====================================================================
   ; DTN BASKET PROTOCOL GRAMMAR (RFC 8610)
   ; =====================================================================

   protocol-version = 1
   coap-status-code = uint .size 1 ; CoAP status codes (RFC 7252)

   ; ---------------------------------------------------------------------
   ; 1. REQUEST BASKET (BASKET REQUEST)
   ; ---------------------------------------------------------------------

   basket-request = {
     ? -1 => uint,            ; Experimentation tag (e.g., 44444)
     0 => uint,               ; Protocol version (protocol-version = 1)
     1 => text / bytes,       ; Unique identifier of the request (req_id)
     ? 2 => text,             ; Optional reply destination (reply_to EID)
     ? 3 => uint,             ; Default lifetime of response bundles (ms/s)
     4 => [* request-item]    ; Array of items ordered by priority
   }

   request-item = {
     0 => uint .default 0,    ; Operation: 0=GET, 1=CHECK, 2=SEARCH, 3=CANCEL, 4=LIST
     1 => text,               ; URI / URN / CID / Tag
     ? 2 => uint,             ; Maximum accepted size in octets (max_size)
     ? 3 => [* (uint / text)],; Accepted formats (default = */*)
     ? 4 => [* bytes],        ; Truncated hashes already owned (have_hashes)



F4JXQ                   Expires 11 February 2027                [Page 3]

Internet-Draft             DTN Basket Protocol               August 2026


     ? 5 => uint,             ; POSIX timestamp (if_modified_since)
     ? 6 => uint              ; Lifetime override for the response of this item (ms/s)
   }

   ; ---------------------------------------------------------------------
   ; 2. METADATA APPLICATION RESPONSE (BASKET RESPONSE)
   ; ---------------------------------------------------------------------

   basket-response = {
     ? -1 => uint,            ; Experimentation tag (e.g., 44444)
     0 => uint,               ; Protocol version (protocol-version = 1)
     1 => text / bytes,       ; Original request identifier (req_id)
     2 => [* item-response]   ; Array of results per item
   }

   item-response = {
     0 => uint,               ; Item index in the original basket (item_idx). Note: Multiple item-responses may share the same item_idx (e.g. for SEARCH).
     1 => coap-status-code,   ; CoAP status code (RFC 7252)
     ? 2 => item-metadata,    ; Metadata of the content bundle
     ? 3 => text              ; Diagnostic message (if error status)
   }

   item-metadata = {
     0 => bytes,              ; SHA-256 hash of the resource (correlation key)
     ? 1 => uint,             ; Size of the resource in octets
     ? 2 => text,             ; MIME type / Format (e.g., "text/markdown")
     ? 3 => text,             ; Explicit URI / URN / CID of the resource
     ? 4 => uint              ; POSIX timestamp of last modification
   }

4.  Detailed Method and Operation Semantics

   The DTN Basket Protocol specifies five different operations denoted
   by the integer value in the op field (key 0) of each request-item in
   a basket.  This section defines the precise operational logic,
   responder behavior, and expectations for each method.

4.1.  GET (op=0) - Resource Retrieval

   The GET operation is used to request the complete, raw payload of a
   specific resource identified by the uri field.

   Upon receiving a successful GET request, the responder node MUST
   perform the following actions:







F4JXQ                   Expires 11 February 2027                [Page 4]

Internet-Draft             DTN Basket Protocol               August 2026


   *  Generate a control bundle carrying a basket-response mapping
      containing an item-response for this query with the coap-status-
      code set to 2.05 Content (69).  The item-metadata MUST be
      populated with the SHA-256 hash (key 0), size (key 1), and MIME
      type (key 2) of the resource.

   *  Emit a separate, native BPv7 bundle containing only the raw
      payload bytes of the resource in its payload block.  This raw
      bundle MUST NOT contain any CBOR wrapper or application-level
      headers.  The correlation between the control bundle and this raw
      data bundle is performed out-of-band by comparing the SHA-256
      hash.

   If the requested resource is not available on the responder, it MUST
   set the status code to 4.04 Not Found (132) and MUST NOT emit a data
   bundle.

4.2.  CHECK (op=1) - Metadata Verification

   The CHECK operation allows a requester to query metadata (such as
   existence, size, hash, or modification date) for a specified resource
   without transferring its actual content payload.  This is highly
   useful for optimizing bandwidth in congested or expensive links.

   The responder node MUST return the metadata in the control bundle
   (basket-response) using the item-metadata structure and set the
   status code to 2.05 Content (69).

   The responder MUST NOT generate any raw data bundle for a CHECK
   operation.

   If the resource does not exist, the responder MUST return the status
   code 4.04 Not Found (132).

4.3.  SEARCH (op=2) - Multi-Resource Discovery

   The SEARCH operation is used for discovering multiple matching
   resources based on criteria specified in the uri field (such as tags,
   wildcard paths, or keyword filters).

   When processing a SEARCH request, the responder node MUST perform the
   following actions:

   *  Find all matching resources in its local store.  Let the number of
      matches be M.






F4JXQ                   Expires 11 February 2027                [Page 5]

Internet-Draft             DTN Basket Protocol               August 2026


   *  Construct a single basket-response containing M individual item-
      response elements.  Each of these response elements MUST set
      item_idx to the index of the original SEARCH query in the basket.
      Multiple item-response maps inside a basket-response array MAY
      share the same item_idx value when the search operation yields
      multiple matching resources for that query.

   *  Generate a separate raw BPv7 bundle for each matched resource,
      totaling M data bundles.

   To prevent traffic amplification attacks in bandwidth-constrained
   environments, the responder SHOULD enforce an upper limit of results
   M_max (e.g., M <= 50).  If the number of matching resources exceeds
   M_max, the responder SHOULD NOT emit the individual data bundles.
   Instead, the responder SHOULD substitute the execution with a LIST
   operation (op=4) to return a single bibliographic index bundle.

4.4.  CANCEL (op=3) - Pending Request Abort

   The CANCEL operation aborts the processing and transmission of all
   bundles associated with a previously submitted request identified by
   the value in the uri field (which maps to the targeted req_id).

   Intermediary store-and-forward nodes processing a CANCEL request MUST
   search their local queues for pending bundles matching the targeted
   req_id (both control bundles and data bundles) and purge them.  They
   MUST also forward the CANCEL bundle downstream.

   The final target node, if still processing the original request, MUST
   immediately abort execution and return a basket-response containing
   an item-response with the status code set to 2.02 Deleted (66).  This
   response bundle MUST NOT be propagated further.

4.5.  LIST (op=4) - Bibliographic Indexing

   The LIST operation is designed to obtain a structured, lightweight
   index of resources matching the search criteria without transferring
   the individual resources.

   The responder node MUST compile a single text document using the
   text/markdown format listing all matching resources.  Each entry in
   the document MUST contain bibliographic fields formatted as an
   AsciiDoc-style front-matter block or key-value list including fields
   such as Title, Author, MIME, Size, POSIX Date, SHA-256 hash, and Page
   count (if applicable).

   The responder MUST emit exactly two bundles:

Internet-Draft             DTN Basket Protocol               August 2026


   1.  One control bundle containing a basket-response mapping with
       status 2.05 Content (69) referencing the compiled document's
       metadata.

   2.  One raw data bundle containing only the compiled text/markdown
       index document.

4.6.  Payload-to-Metadata Correlation

   Raw BPv7 data bundles carry no application-level headers, metadata,
   or CBOR encapsulation.  Instead, receiving nodes MUST use the
   following correlation procedure to bind incoming unencapsulated data
   bundles to their corresponding request context:

   1.  Upon receiving an unencapsulated data bundle, the receiver MUST
       compute the SHA-256 digest of the bundle's payload block.

   2.  The receiver MUST query its stored basket-response tables (or
       active request context) for an item-metadata entry where Key 0
       (hash) matches the computed SHA-256 digest.

   3.  Upon a successful match, the data payload IS bound to the
       corresponding request identifier (req_id) and item index
       (item_idx).

5.  Node Behavior and Execution Semantics

5.1.  Requester Operations

   The sending node MUST assign a unique req_id.  It MUST order the
   elements of the request-item array in descending order of priority
   (index 0 representing the highest priority).

5.2.  Forwarder and Intermediary Node Operations

   An intermediary node possessing in its local cache all or part of the
   requested resources MAY generate the corresponding response bundles.
   When responding partially:

   *  It MUST transmit the application bundle basket-response containing
      the resolved items to the reply_to or the BPv7 source.

   *  It MUST forward the original basket-request bundle strictly
      unchanged to adjacent nodes to maintain BPSec integrity
      ([RFC9182]).

5.3.  Responder Operations and Lifetime Mapping

   When generating a response bundle (metadata or raw content), the
   responder MUST configure the Lifetime field of the BPv7 Primary Block
   according to the following order of precedence:

   1.  The value of the item.lifetime field (key 6) if defined.

   2.  The value of the basket-request.default-lifetime field (key 3) if
       defined.

   3.  The default configuration of the local responder node.

6.  CoAP Status Codes Mapping

   The coap-status-code field of the item-response component MUST use
   the registry defined by RFC 7252 [RFC7252].  The following codes are

7.  Security Considerations

7.1.  Amplification Attacks

   The SEARCH operation (op=2) presents a traffic amplification risk
   (transmission of 1 + M bundles).  Responder nodes SHOULD impose a
   maximum result limit (e.g., M <= 50).  Beyond this limit, the
   responder SHOULD substitute the execution with a LIST operation
   (op=4) and return a single report.

7.2.  Content Correlation and Verification

   The receiving node MUST validate the integrity of each raw content
   bundle received separately by computing its SHA-256 hash and
   comparing it with field 0 of the item-metadata structure transmitted
   in the basket-response bundle.

   *  The registration of the MIME types application/dtn-basket-

   *  The creation of the _DTN Basket Operations Registry_ for managing

A.3.  Scenario 3: Delta Synchronization with Hashes (SEARCH)

   The requester searches for files tagged as "emergency-medical-guide"
   but already has two of the manuals.  To prevent sending duplicate
   documents, the requester lists truncated 8-byte hashes of the manuals
